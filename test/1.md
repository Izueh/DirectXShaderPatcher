### Verified Findings While Adding an SRV to `0x965B1360.ps_6_6.cso`

#### 1. `SetHLSLType()` had to use the global pointer type in this DXC branch

The working fix in this repository was changing resource registration from `SetHLSLType(gv->getValueType())` to `SetHLSLType(gv->getType())`.

What we verified locally:

* Using the pointee type broke the SM 6.6 path during DXIL metadata refresh with `DXC_E_INCORRECT_DXIL_METADATA (0x80AA000F)`.
* Using the global pointer type allowed the patched shader to pass LLVM verification, serialize into a container, and reload successfully.
* This matches the expectations in DXC's `DxilMDHelper::EmitDxilResourceBase()`, which compares `GetHLSLType()` against `GlobalSymbol->getType()` and may bitcast the global symbol to the recorded HLSL type.

Current confidence:

* Verified for this repository and this SM 6.6 shader.
* Not yet generalized across all shader models.

---

#### 2. Resource refresh had to follow the narrow DXC-style path

The working metadata update sequence after adding the SRV was:

1. `EmitLLVMUsed()`
2. `ReEmitDxilResources()`
3. `CollectShaderFlagsForModule()`
4. `UpgradeToMinValidatorVersion()`
5. `UpdateValidatorVersionMetadata()`

What we verified locally:

* Calling the broader full-metadata refresh path too early caused `DXC_E_INCORRECT_DXIL_METADATA` on this shader.
* Switching to the narrower resource-focused path made the `--texture-only` CLI flow succeed.
* This is consistent with nearby DXC passes that mutate resources and then call `ReEmitDxilResources()`.

---

#### 3. The injected SRV needed complete resource registration plus `llvm.used`

The SRV path only became stable once the new resource had all of the following set:

* `GlobalSymbol`
* `GlobalName`
* `HLSLType`
* `SpaceID`
* `LowerBound`
* `RangeSize`
* `ID`
* `Kind(Texture2D)`
* `CompType(F32)`
* `SampleCount(0)`
* `RW(false)`

The backing global also had to be retained in `llvm.used`.
For downstream decompilers, a placeholder marker struct was not sufficient. The
injected SRV had to use the canonical `class.Texture2D<vector<float, 4> >`
LLVM type so tools could infer the resource data type from the pointer.

What we verified locally:

* The in-memory SRV table increased from 1 to 2 entries.
* After metadata refresh and container serialization, the patched container could be reparsed and the added SRV was still present.
* The successful round-trip test now checks that `MyTex` survives reload with the expected `t1, space0` binding.
* `dxc -dumpbin` now shows `@MyTex = external constant %"class.Texture2D<vector<float, 4> >", align 16` instead of the previous placeholder `%MyTex_Texture2D_t` declaration.

### Findings That Are Plausible But Still Unverified Here

#### 1. `STAT` and `RDAT` chunk rebuilding

It is plausible that stale `STAT` and `RDAT` chunks will cause reflection and tooling mismatches after DXIL mutation.

What we have not yet verified in this repository:

* Whether `ID3D12ShaderReflection`, PIX, or RenderDoc will miss the injected SRV if those companion chunks are left stale.
* Whether DXR library scenarios require `RDAT` rebuilding for this specific patch flow.

---

#### 2. Post-pass validator signing requirements

It is plausible that patched containers will need a validator/signing pass before normal runtime deployment.

What we have not yet verified in this repository:

* Whether the generated container is accepted by `ID3D12Device::CreatePipelineState` as-is on a normal runtime path.
* The exact failure mode on a production driver if validator state is stale.

---
